## Convergence note — integer ops on float-only hardware (#2729 / #3802 / #4383)

Posting this separately from the review so it doesn't get buried, and because it
concerns three PRs rather than one. Spyre's ALUs are floating-point only, so every
integer op has to be emulated by promoting to float, and we have been growing one
bespoke mechanism per op family. This PR is the first one to push back on that, so
it's the right place to write down where the rest should land.

### Where we actually are

| mechanism | op family | layer | promotion source |
|---|---|---|---|
| `with_int64_fallback` | `add`, `mul`, `sub`, `minimum`, `maximum`, `prod_dim` | lowering | none — hardcoded "any int64 → fp32 → int64" |
| `_cmp_operand_dtype` / `_lower_cmp_impl` (#3802) | comparisons | lowering | `_promoted_dtype`, **dtype-only**, all-bool carve-out |
| `lower_where` (#4383) | `where` | lowering | `_promoted_dtype`, **dtype-only**, no carve-out |
| `_div_operand_dtypes` (this PR) | `div`, `true_divide`, `floor_divide` | lowering | `_promoted_dtype`, **ndim-aware** (in name only — see item 1), no carve-out |

The good news: this PR collapsed what was going to be a fourth *mechanism at a new
layer* (the `spyre::adapt_dtype` custom ops in the decomposition pass) into two
shared lowering-layer helpers, `_promoted_dtype` and `_convert_to_dtype`, and
refactored #3802's and #4383's code onto them. Everything that computes a
promotion now goes through one function. That is the right shape and the right
layer, and it's worth saying so explicitly.

What remains is a difference in *how* the shared helper is called. An earlier
revision of this comment called that a correctness bug; I tested the claim and it
is not one — item 1 below is the corrected version.

### 1. The shared helper has two calling conventions (latent only — no change requested)

`_promoted_dtype` accepts either IR nodes or bare `torch.dtype`s, and
`_to_elementwise_arg` treats them differently:

- an IR node becomes `torch.zeros([1] * ndim, dtype=...)` — **rank preserved**
- a bare dtype becomes `torch.empty(0, dtype=...)` — **always rank 1**

PyTorch gives 0-dim tensors lower promotion priority than dim≥1 tensors within a
category, so in isolation the two branches disagree for `fp32[0-dim]` vs
`fp16[1-dim]` (fp16 rank-preserving, fp32 rank-erasing). `_div_operand_dtypes`
passes IR nodes; `lower_where` and `_cmp_operand_dtype` pass `t.get_dtype()`.

**I originally wrote that this costs us an aten-supported `where` case that the
ndim-aware convention would have compiled. That was wrong on every count** —
asserted from reading, not measured. Correcting it, because the real reason
matters for where this family is going:

```python
cond = torch.rand(256) > 0.5
a0   = torch.tensor(2.5, dtype=torch.float32)   # 0-dim fp32
b1   = torch.randn(256).to(torch.float16)       # 1-D fp16
torch.where(cond, a0, b1)                       # aten: fp16
```

`a0` and `b1` have **different element byte sizes**. Promoting `b1` to fp32 makes
the tensor staggered, and torch-spyre has no EA adjustment operator yet, so this
whole class is an **expected fail** today — an architectural gap, not a
calling-convention defect. And the *intended* operation is exactly what
`lower_where` already asks for: promote to fp32, adjust the EA, run `where` in
fp32. The fp32 promotion is the right answer.

Three measurements at `1c4e621b` that back that up:

1. **The ndim-aware convention is strictly worse here.** I patched both
   `_promoted_dtype` calls in `lower_where` to pass the IR nodes and re-ran the
   example. It does not stay fp16 and compile — it fails, and not cleanly:

   ```
   InductorError: SubprocException ... Name=sdsc_fused_where_0
     RuntimeError: dbo-opt failed with exit code 1
     .../ddl_templates/quantization_double_pad.ddl:268:25: error: Specified
       dimension of parametric loop operation is m...
     error: sbf-ddc: DtException: Illegal ddl
   ```

   So the current `Unsupported: ... mixed EA` refusal is the **better** of the two
   outcomes — a frontend rejection instead of a backend compiler crash.

2. **For `div` the two conventions are provably equivalent.** `aten.div.*` is
   registered with `broadcast=True`, so Inductor equalizes operand ranks *before*
   the lowering runs — `_div_operand_dtypes` is ndim-aware in name only. Traced on
   the same 0-dim input:

   ```
   _div_operand_dtypes(torch.float32[256], torch.float16[256]) -> comp=fp32 result=fp32
   ```

   Both operands arrive rank 1, so the 0-dim-vs-dim≥1 asymmetry can never
   materialize and div lands on **the same fp32 answer `lower_where` gives**.

3. **Where there is a real hole it is pre-existing and generic.** The equal-rank
   mixed case — this PR's own `fp32_fp16_1d256` `expect_fail` — rejects correctly.
   The 0-dim variant satisfies the gate's "must broadcast (stick dimension size
   1)" condition, slips through, and returns fp32 where aten returns fp16 with
   wrong values (most likely the staggered fp32-from-fp16 readback). That is not
   div-specific and not new:

   | op (0-dim fp32, 1-D fp16) | aten | spyre | wrong |
   |---|---|---|---|
   | `add` *(pre-existing lowering)* | fp16 | fp32 | 217 / 256 |
   | `mul` *(pre-existing lowering)* | fp16 | fp32 | 223 / 256 |
   | `a / b` *(this PR)* | fp16 | fp32 | 223 / 256 |
   | `torch.where` *(#4383)* | fp16 | — | raises `Unsupported` |

   `add` and `mul` predate all three PRs, so this belongs to the missing EA
   adjustment operator — and `where` is the only one of the four that behaves
   safely.

**So: no change requested here.** What is left is hygiene — `_promoted_dtype`
treating node rank and bare-dtype rank differently is a trap for a future caller
even though none can reach it today, and one convention plus a docstring line
would close it. The substantive question is downstream of the EA adjustment
operator: once mixed element byte sizes can be computed, aten's result dtype for
`fp32[0-dim]`/`fp16[1-dim]` is fp16 while the compute must be fp32, so `where`
will need the comp/result split `_div_operand_dtypes` already documents. That is
the right moment to settle the convention. (Related live territory: #5093's last
failing `eq` case is blocked by #3802's own 0-dim carve-out.)

### 2. The all-bool carve-out should be shared or justified

#3802 added an all-bool carve-out to `_cmp_operand_dtype`: device bools are
already stored in an fp16/fp32-width numeric format, so promoting them inserts a
conversion that buys nothing and can be EA-changing. That reasoning is not
specific to comparisons, but neither `lower_where` nor `_div_operand_dtypes` has
it. (For div it happens not to matter — `bool/bool` `floor_divide` raises
`NotImplementedError` in aten, so that row of this PR's promotion table is
unreachable. For `where` it is reachable.)

**Proposal:** either lift the carve-out into `_promoted_dtype` behind a flag, or
drop a comment at the two sites that don't have it saying why they don't need it.
I raised the same gap on #4383; it is cheaper to settle it once in the shared
helper than three times.

### 3. `with_int64_fallback` is the one that still needs subsuming

Six op families still go through the pre-existing path, which is structurally
weaker than the three converged ones: it keys on "does any operand have dtype
int64", ignores promotion entirely, and unconditionally casts the result back to
int64. It cannot express the comp-dtype / result-dtype split that all three newer
mechanisms need — which is precisely the distinction that makes `div` and `where`
correct for mixed int/float operands.

**Proposal:** a single

```python
with_float_compute(fn, *args, kind=INT_TO_FLOAT, result_kind=NO_OPMATH)
```

built on `_promoted_dtype` + `_convert_to_dtype`, replacing `with_int64_fallback`
at its six call sites. The two-dtype pattern this PR documents in
`_div_operand_dtypes` is already the general form; `with_int64_fallback` is the
special case where comp is hardcoded fp32 and result is hardcoded int64.

I am **not** asking for that in this PR — it is a separate change with its own
test surface, and this PR has done more than its share of the consolidation
already. Flagging it so it doesn't get forgotten once the three converge.

### 4. What is genuinely op-specific and should stay that way

Worth being explicit, so convergence doesn't overreach: the remainder-based
quotient correction in `_lower_div_impl` is *not* dtype plumbing and should not be
generalised. It exists because Spyre's divider undershoots, and (per finding 1 of
my review) it is only as accurate as its compute dtype — reliable in fp32,
unreliable in fp16. That is a property of division, not of integer emulation.

### Merge order

- **#4383** (`where`): approved ×2, owns the `constants.py` `"where"`→`"where3"`
  line. This PR correctly dropped its competing hunk. Lands first.
- **#3802** (cmp): the semantic baseline — it is where the all-bool carve-out and
  the documented >2^24 caveat came from — but it is still blocked on a second
  approver. The fp32 domain caveat in finding 5 of my review is the same gap it
  already closed with `bigint` cases; copying that pattern here is cheap.
- **#2729** (this PR): rebases onto whichever lands.
- Relevant precedent: **#4029** for why Spyre decompositions must register the
  overload and never the packet — this PR's move of `floor_divide` to a lowering
  side-steps that class entirely, which is the better fix.

Happy to take item 3 — and the item 1 hygiene cleanup — as follow-up PRs myself
if that's easier than piling them onto this one.
